# Stage 1.2.5 — вход через существующего Telegram-бота

Эта версия продолжает Stage 1.2. Сайт, Fastify API и webhook остаются в существующем Render Web Service. Prisma, единая Telegram identity, тарифы, заказы, подписки, демо-VPS и старые тесты сохранены. Отдельный polling-процесс `apps/bot` по-прежнему не запускается: рабочие обработчики находятся в `apps/api/src/telegram.ts` и используют общий SubscriptionEngine.

## Три способа входа

1. На странице `/#/login` сайт создаёт запрос на 5 минут и показывает число для сверки. Пользователь открывает `vpnaxon_bot` обычной ссылкой, сверяет число и подтверждает собственный запрос. Сайт опрашивает Backend раз в 3 секунды и обменивает подтверждение на сессию. Обновление страницы восстанавливает ожидание; авторизация привязана к HttpOnly cookie браузера. Идентификатор запроса без cookie и отдельной случайной deep-link capability не даёт входа.
2. В боте `/login` или «Личный кабинет / Войти на сайт» выдаёт ссылку на 3 минуты. Токен находится только в URL fragment и удаляется из адреса до загрузки Telegram SDK. Открытие ссылки и предпросмотр её не используют: нужен явный POST после «Продолжить», затем подтверждение в боте владельца. Пересланная ссылка не создаёт сессию чужого аккаунта.
3. `/code` или «Получить код входа» выдаёт случайный восьмизначный код на 5 минут. Пользователь сам вводит код на сайте. Новый код отменяет предыдущий. Это одноразовый секрет: его нельзя пересылать или вводить на других сайтах.

Все способы используют `UserIdentity(TELEGRAM, числовой User ID)`, а не username. Username нужен только для открытия бота. Первый проверенный контакт с ботом создаёт аккаунт; последующие входы возвращают тот же UUID. Смена аккаунта в уже вошедшем браузере требует предварительного выхода.

## Защита

- Webhook принимает update только с существующим `TELEGRAM_WEBHOOK_SECRET`. Пользователь должен быть настоящим отправителем в личном чате с совпадающим chat ID. Браузер не может передать Telegram ID для создания сессии.
- Запросы, ссылки и коды обмениваются атомарно под транзакционным PostgreSQL advisory lock; повторное и конкурентное использование не создаёт вторую авторизацию.
- Код хранится как HMAC-SHA256 с domain separation и серверным ключом бота. Случайные 256-битные токены ссылок, deep links и сессий хранятся только в виде SHA-256. Токен бота не попадает в браузер.
- В production: `__Host-` cookie, HttpOnly, Secure, SameSite=Lax, Path=/, без Domain. Cookie ожидания отдельна от действующей сессии: создание запроса не выбрасывает пользователя из аккаунта.
- Проверка кода ограничена по реальному transport IP и cookie браузера (8 попыток/5 минут), значению кода (5/5 минут), а также общим пределом 100/5 минут. Новые запросы — 10/5 минут; выдача ботом — 3/5 минут на пользователя и вид секрета. Счётчики сохраняются в PostgreSQL и переживают перезапуск. Заголовки X-Forwarded-For не используются как доверенная идентичность: на общем reverse proxy ограничения могут быть консервативнее.
- Auth API использует POST, точный разрешённый Origin и `x-shared-vps: 1`. Ответы и HTML не кешируются. HTML отдаёт `Referrer-Policy: no-referrer`; fragment никогда не передаётся HTTP-серверу. Журнал запросов не содержит query string, cookie, коды или тела сообщений.
- Входящие deep-link capabilities хешируются до сохранения в очереди webhook. Исходящие коды и ссылки не сохраняются в `telegram_updates.response`. После сбоя между выдачей и доставкой бот может предложить запросить новый секрет вместо повторной доставки старого — это сознательная защита хранения.
- При выходе отзывается текущая сессия и все ожидающие запросы этого браузера. Другие устройства сохраняют свои сессии. Технические auth-записи очищаются через сутки после истечения срока; пользовательские данные не удаляются.

Сверка числа и предупреждение в боте защищают от подтверждения чужой просьбы. Никогда не подтверждайте запрос, который не создавали сами; сознательную передачу одноразового кода или подтверждение фишингового deep link программно исключить нельзя.

## Миграция и Render

Добавлена только миграция `20261025000000_bot_login`: новые таблицы `login_requests`, `login_grants`, `auth_limits`, индексы и внешние ключи. Старые таблицы и миграции не изменяются, reset/db push не используются.

Порядок выпуска через браузер:

1. Дождаться зелёного Verify foundation для PR и проверить diff.
2. После объединения в main выполнить GitHub Actions → **Cloud database - migrate and seed** → Run workflow → main. Он использует существующий секрет **NEON_MIGRATION_DATABASE_URL** с direct URL нового проекта `patient-queen-83814443`, production `br-rapid-butterfly-b4t863o9`. Не использовать другую Neon-базу. Миграция сначала проверяется на изолированной ветке production.
3. После успешной миграции опубликовать этот коммит в существующий Render **shared-vps-api**. Команды сборки/запуска и план не меняются. `DATABASE_URL` остаётся pooled URL той же production.
4. В Render → shared-vps-api → Environment проверить имена **TELEGRAM_BOT_TOKEN**, **TELEGRAM_WEBHOOK_SECRET**, **TELEGRAM_BOT_USERNAME=vpnaxon_bot**, **PUBLIC_ORIGIN=https://shared-vps-api.onrender.com**, **CORS_ORIGINS=https://shared-vps-api.onrender.com**. Токен и секрет вводятся только в защищённые поля Render. Новых секретов для Stage 1.2.5 нет. **TELEGRAM_LOGIN_CLIENT_ID** и **TELEGRAM_LOGIN_CLIENT_SECRET** для этого входа не нужны; существующий необязательный Client ID можно удалить позднее.
5. При запуске API проверяет существующий webhook и регистрирует его, только если он пуст или уже указывает на этот API. Чужой webhook автоматически не заменяется. Накопленные update не отбрасываются. При конфликте лог содержит безопасное сообщение `Telegram webhook setup pending`; в этом случае владелец проверяет текущий webhook и старый polling. ADMIN для первого запуска бота не требуется.
6. Открыть `/health`, `/ready`, `/api/v1/auth/config` и `/#/login`, проверить три способа со своим Telegram. На сайте после успеха должны появиться «Telegram · Личный кабинет», подписки и история. Повторный вход должен вернуть тот же UUID.

Чтобы исключить короткое окно несовместимости при первой миграции, перед merge временно выключите Auto Deploy в Render, примените миграцию workflow и только затем выполните Manual Deploy проверенного коммита. После успешной проверки можно вернуть After CI checks pass. Blueprint Auto Sync оставьте выключенным.

## Проверки и пределы готовности

Автоматические тесты охватывают создание и повторное использование identity, привязку браузера, чужое подтверждение, forged webhook/Origin, истечение, отмену, перезагрузку через восстановление запроса, одновременные попытки, повторное использование, HMAC и отсутствие открытых кодов в очереди, перебор, смену аккаунта и выход. Старые интеграционные тесты продолжают проверять покупки, продления, демо-VPS и обновление заполненной базы.

Конкретные результаты запуска, ссылки CI/PR и проверку migration branch следует фиксировать в отчёте выпуска. Тестовый transport Telegram не равен настоящей доставке. Реальные Android/iOS, подтверждение через телефон с компьютера, доставка в Telegram и итоговый Render требуют отдельной ручной проверки владельцем. До неё нельзя объявлять production-вход полностью проверенным или Stage 1.3 готовым.

Официальные протоколы: [Telegram deep links](https://core.telegram.org/bots/features#deep-linking), [Bot API webhook](https://core.telegram.org/bots/api#setwebhook). Free Render может засыпать: первый запрос/ответ бота после простоя может задержаться до запуска сервиса; гарантии 24/7 для демонстрации нет.
