# Фактическая проверка Stage 1.2 · 16.10.2026

## Среда и результат

Windows, Node **22.22.2**, pnpm **10.34.4**, Prisma **6.19.3**, настоящий
PostgreSQL **16.13** на loopback. В CI настроен postgres:16.13-alpine; версия
БД совпадает, ОС/контейнер отличаются. Docker в этой среде не установлен.

**49 модульных + 24 интеграционных = 73 успешных теста.** Исходные 48 модульных
и 9 интеграционных сохранены. Прежний тест «admin endpoint отсутствует» обновлён
на «admin endpoint требует авторизации» (401), потому что в Stage 1.2 endpoint
реализован; отдельно проверяется 403 для обычного пользователя. SQL-защита не ослаблялась.

Успешно выполнены:

- `pnpm install --frozen-lockfile --store-dir …` (локальный кеш, lockfile сохранён).
- `pnpm build`, `pnpm typecheck`, `pnpm db:validate`.
- `pnpm test`, `pnpm test:integration`; после заключительных изменений —
  `pnpm build:cloud:unified`, `pnpm typecheck` и оба Vitest config напрямую:
  **49/49 и 24/24** на окончательном исходном коде.
- `pnpm build:cloud:web` с fixture HTTPS origin и canary server secrets.
- `pnpm verify:web-artifact`: секреты сервера и loopback fallback отсутствуют
  в клиентском JS; в localStorage используется только ключ темы.
- `pnpm cloud:validate`: Render YAML по сохранённой официальной JSON Schema,
  команды сборки, ручные миграции, CI и наличие проверки клиентского артефакта.

Все тесты базы создают случайные схемы и очищают только свои схемы. Дополнительно
проверен **upgrade заполненной Stage 1.1 базы**: применение foundation SQL,
регистрация прежней миграции, создание заказа/слота/активной подписки/доступа,
затем migrate deploy Stage 1.2. UUID, сроки, история и доступ сохранились;
удаление связанного места по-прежнему отклонено Prisma **P2003**.

## Браузерная проверка

Сайт запущен с настоящей отдельной PostgreSQL-схемой. Для QA использована только
локальная тестовая сессия; вспомогательный маршрут **не входит в исходники проекта
и ZIP**. Это не проверка живого Telegram Login.

В браузере выполнены покупка четвёртого пользователя, просмотр новой подписки,
reload, админка со схемой мест 3 + 1, создание обращения и подключение/инструкция.
Проверены светлая/тёмная тема, ширины 320/390/1280. Широкие таблицы прокручиваются
внутри контейнера, страница не имеет горизонтального переполнения. Полная матрица
мобильных устройств/iOS/Android не проходилась. Локальные сервисы после QA остановлены.

## Что НЕ проверялось удалённо

- Настоящий Telegram token, BotFather Allowed URLs, live OIDC/JWKS-claims,
  доставка сообщений и Mini App в мобильном Telegram.
- Реальный Render deploy, cold start webhook, Neon pooling/квоты.
- Запуск workflow на GitHub Actions Linux runner.

Проверены локальная логика и криптография на подписанных тестовых данных,
официальный адрес/методы Login SDK, облачные сборки и конфигурация. Это не заменяет
контрольный запуск владельцем аккаунтов по cloud-deployment.md. Секреты не запрашивались.

## Ограничения и отложенные функции

- Free Render не даёт 24/7: во сне нет обработки очереди и интервалов. После
  пробуждения данные и задачи восстанавливаются, но своевременная доставка не гарантирована.
- Telegram sendMessage может повториться при неопределённом сетевом исходе.
  Бизнес-операции идемпотентны, exactly-once доставки сообщений не обещается.
- До пяти автоматических попыток. Ошибки заказов видны в админке; зависшие updates
  после лимита диагностируются/перезапускаются владельцем БД по инструкции.
- Нет отдельной production очереди, backoff, dead-letter UI, автоматической очистки
  сессий/inbox, пагинации сверх лимита 500 строк и лимитов запросов на аккаунт.
- Нет проактивных напоминаний об истечении/продлении вне пользовательского действия:
  активация подтверждается ответом бота или уведомлением сайта.
- Настоящие платежи, Aeza, VPS и VPN не реализованы по границам Stage 1.2.

Основные сценарии Stage 1.2 реализованы и проверены локально. Облачная приёмка
и живая Telegram-приёмка остаются **невыполненными**. Stage 1.3 не начинался.
