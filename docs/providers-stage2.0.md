# Stage 2.0 · подключение провайдеров
Проверка официальных контрактов: 09.11.2026. Все внешние адаптеры — SANDBOX only, не зарегистрированы в production routes. APP_MODE остаётся demo; DB CHECK не допускает LIVE. Наличие API-кода не равно одобрению продавца или проверенному vendor sandbox.

## Telegram Stars — основной канал Telegram
Реализованы реальные HTTP-контракты createInvoiceLink, answerPreCheckoutQuery, refundStarPayment, getStarTransactions на https://api.telegram.org/bot<TOKEN>/test/<METHOD>. Строка /test/ неизменяема; production Bot API этим адаптером недостижим. Один XTR price, provider_token пустой, без subscription_period/автопродления. Цена Stars не выводится из 170 ₽: требуется отдельная явная утверждённая quote. Quote фиксируется в PaymentOperation, precheckout проверяет сумму/валюту, payload, Telegram ID, состояние заказа и актуальное принятие условий.
Оплата только после подлинного successful_payment или подтверждённой записи getStarTransactions; precheckout не выдаёт подписку. Webhook secret обязателен, charge связан с конкретным пользователем/заказом. Возврат не отражается в финансовом журнале от одного успешного запроса: нужны refunded_payment или подтверждённая транзакция. Reconciliation просматривает до 500 транзакций за проход, проверяет user/payload/charge/amount, сначала capture, затем refund. Дальняя история за пределами окна требует контролируемой пагинации/разбора, не автоматического вывода «не оплачен». Конфликтующие charge IDs блокируются для ручной сверки.
Нужны: законный уполномоченный продавец, принятие официальных условий, отдельно разрешённый тестовый бот в официальной Telegram test environment и его токен/secret в защищённой CI Environment, затем тестовые покупка/повтор/возврат и доказательства. Существующий production @vpnaxon_bot нельзя переиспользовать как тестовый или менять его webhook. Новый тестовый бот не создан без разрешения. Потребуются утверждённые /terms и /paysupport, проверка расчётов/налогов и согласование XTR-цены до LIVE.
Источники: https://core.telegram.org/bots/payments-stars ; https://core.telegram.org/bots/api ; https://core.telegram.org/bots/webapps#testing-mini-apps

## RollyPay — первый кандидат самостоятельного сайта
API: https://rollypay.io/api/v1. Реализованы POST /payments (test:true, X-Test-Mode:true, payment_method:sbp), GET /payments/{id}, сырая HMAC-SHA256 timestamp.body с X-Signature/X-Timestamp. X-Nonce — новый на каждый запрос, это anti-replay, НЕ серверная идемпотентность. Защита от повторного создания — постоянный ProviderAttempt; после таймаута не повторяем POST. После подписанного callback сверяется текущее состояние GET, поэтому доставка старого expired после paid не отменяет оплату. Late paid/chargeback не теряются. Redirect не является доказательством оплаты. Совпадение order, currency, amount и test обязательно.
Официальный sandbox принудительно имитирует СБП и не меняет баланс; возвраты в нём НЕ поддерживаются. Адаптер refund явно отказывает, LIVE отсутствует. Полноценный реальный возврат RollyPay не объявляется реализованным: нужен подтверждённый refund API/договор и проверяемая среда. Не придумываем endpoint.
Внимание: официальная модель предполагает конвертацию поступлений в USDT. Это отдельный договорный, расчётный, налоговый и валютный вопрос для выбранного продавца, а не автоматически подходящий российский эквайринг. Требуются письменное подтверждение допустимости VPN/продавца, идентификация, условия вывода/комиссий/возвратов/оспаривания и решение о законности расчётов. Не создавались кошельки/кассы и не принимались договоры.
Для sandbox: получить кассу/API key/signing_secret безопасно, не в чат; настроить callback только в отдельно изолированном test harness с raw body. По официальной странице test payment pay_url показывает кнопки симуляции; владелец может выбрать paid/failed. После проверки capture/duplicate/reconcile зафиксировать provider IDs без секретов. Пока аккаунта нет, выполнены только offline contract fixtures.
Источники: https://docs.rollypay.io/api/authentication/ ; https://docs.rollypay.io/api/payments/ ; https://docs.rollypay.io/api/testing/ ; https://docs.rollypay.io/api/callbacks/ ; https://rollypay.io/offer

## CloudPayments — резерв
Реализованы /orders/create (hosted URL, без Email/SMS/recurring), /v2/payments/find, /payments/get, /payments/refund, Basic auth и X-Request-ID. Только Public ID с test_api_ и обязательный TestMode в доказательствах. Content-HMAC от точного URL-encoded UTF-8 тела, base64 SHA256; event kind определяется URL test handler, не телом/заголовком клиента. Refund webhook не содержит TestMode/Currency: дополнительно читается оригинальная test-транзакция и сверяется исходный charge/order/amount/currency. Частичный refund не принимается как полный. Найденная последняя refund/payout/decline не выдаётся за capture.
Provider idempotency хранит результат около часа; долговечная защита AXON не полагается на этот срок и не пересылает UNKNOWN. Нужны договор/проверка продавца, отдельный TEST terminal, API Secret в защищённой среде, включённые POST notifications, проверка card/SBP-функций и возврата. Hosted invoice не является доказательством доступности СБП на данном merchant terminal. Sandbox с настоящим аккаунтом не выполнен.
Источник: https://developers.cloudpayments.ru/

## Aeza — закрытый gate
Действующая оферта https://aeza.net/ru/terms опубликована 03.11.2026, EZ Infrastructure Limited. П.3.22 исключает поддержку ПО обхода блокировок; это не подтверждение разрешения коммерческого VPN/перепродажи. Доступная официальная публичная API-документация https://github.com/AezaGroup/dev-docs архивная; текущий контракт изменения ресурсов не подтверждён. Сторонние endpoints не заменяют подтверждение Aeza.
Поэтому AezaBlockedProvider не делает HTTP-вызовов: quote/lookup/create/renew/terminate явно заблокированы. Подготовлены проверка свежести/бюджета quote, положительный список только собственных AXON-ресурсов с durable operation и scope, отдельные metadata access IDs максимум для трёх клиентов. ResourceFoundation из Stage 1.9 продолжает давать проверенный DEMO; реальный VPN control plane/агент, установка протокола и выдача секретов не притворяются готовыми.
Категорически запрещён SWE-PROMO: deny по имени/ID даже при ошибочном allowlist; никаких изменений/перезагрузок/чтения личной конфигурации. Его нельзя добавлять в scope AXON. Создание ресурса после потери ответа никогда не повторяется до достоверного lookup; без подтверждённого lookup API реальная покупка остаётся заблокированной.
Нужно получить через кабинет Aeza (самостоятельно, без отправки токена в чат): актуальную официальную спецификацию API/version/auth, sandbox/безопасный отдельный тестовый scope, поддержку client reference/idempotency/lookup после потери ответа, актуальные цены/налоги/продления/завершения; письменное разрешение коммерческого VPN/трёх независимых клиентов/перепродажи с учётом юрисдикции. Вопросы можно оформить одним тикетом; агент никому ничего не отправлял. Далее отдельное разрешение владельца и лимит бюджета на НОВЫЙ независимый VPS AXON. До этого реальные вызовы запрещены.

## Запуск изолированного harness
IntegrationService принимает db, адаптер и LegalService; sandboxWebhooks устанавливается только в независимом test Fastify и отвергает NODE_ENV=production. Production buildApp НЕ вызывает эту функцию. Тестовый webhook URL /sandbox/webhooks/event (Stars/Rolly) или /sandbox/webhooks/pay|refund|fail (CloudPayments) принимает raw body, проверяет подпись, сохраняет событие прежде ACK. Настраивать внешние callbacks можно только после отдельного согласования доступного HTTPS test endpoint; существующий production webhook не изменять.
Фиктивные TEST-only тексты в интеграционных тестах — не публичные юридические документы. Для фактических sandbox испытаний отделить тестовую политику от коммерческой оферты и не подменять настоящие пользовательские согласия тестовыми. После sandbox-подтверждений остаётся отдельное контролируемое включение LIVE (не входит в этот PR).
