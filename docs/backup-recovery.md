# Защита данных и восстановление

Только существующий Neon `patient-queen-83814443`, production `br-rapid-butterfly-b4t863o9`, neondb. При инспекции 26.10.2026: Free, PostgreSQL 18, `history_retention_seconds=21600` — окно истории 6 часов. Это короткий PITR, а не бессрочный независимый backup. Схема миграции дополнительно проверяется CI на PostgreSQL 16.13.

Согласно [Neon History window](https://neon.com/docs/postgres/backup-restore/history-window), Free ограничен 6 часами и 1 GB истории. Тарифные возможности нужно проверять перед инцидентом: проектное окно задаёт доступную глубину восстановления. Настройку retention не меняли, платные snapshots/backup schedules не включали. [Документация Instant restore](https://neon.com/docs/postgres/backup-restore/branch-restore) описывает восстановление root branch, затрагивающее все её данные и схему; child branches имеют иные ограничения.

## Перед выпуском

1. Зафиксировать точные SHA API и migration, последний зелёный CI, число пользователей, заказов, подписок, тарифов, активных мест и список завершённых Prisma migrations. Использовать агрегаты, не выгружать персональные данные в GitHub.
2. Проверить оставшийся бесплатный лимит веток/хранилища. Создать отдельную pre-release ветку от текущей production в том же проекте; пометить время и связанный выпуск. Не сбрасывать старые тестовые ветки. Ветку с копией данных считать такой же приватной, как production.
3. На изолированной validation-ветке применить сохранённую миграцию, проверить старые данные и бизнес-ограничения. Не редактировать `_prisma_migrations` вручную. После проверки отключить compute, сохранив ветку до решения о выпуске.
4. Получить согласие на production-выпуск. Отключить Auto-Deploy, выполнить merge, штатный direct-URL workflow миграции и только затем Manual Deploy точного коммита. Проверить endpoints, реальные пользовательские сценарии и heartbeat. Возвращать Auto-Deploy после проверки.

## Если релиз неудачен

- Остановить дальнейшие изменения и фоновые отправки; записать момент инцидента и безопасные симптомы. Не выполнять reset/db push, не удалять job/business rows и не запускать массовую повторную рассылку.
- При ошибке только API после добавочной миграции предпочтителен rollback к прежнему коммиту Render с сохранением расширенной схемы. Старые поля и таблицы совместимы. Перед откатом обработчика остановить новую обработку; неопределённые sends проверить отдельно. Восстановление старого API тоже требует согласования, если может изменить данные.
- Если повреждены данные, сначала создать изолированную ветку на нужном историческом состоянии внутри доступного окна и проверить там миграции, counts, ключевые связи заказ→подписка→место, уникальности и историю. Это не разрешение перезаписывать production.
- После инцидента production могла получить новые регистрации, заказы, продления и подтверждения. Полный restore к старой точке удалит эти изменения. Сохранить текущую ветку и составить план сверки/переноса новых данных по стабильным ID и audit events. Не «сливать» базы SQL без проверки конфликтов.
- Показать владельцу конкретную точку восстановления, затрагиваемые данные, новые записи после неё и способ их сохранения. Только после явного подтверждения выполнять restore/promote/переключение подключений. Проверять уже восстановленную систему на изолированной ветке до окончательного переключения.

## Проверка восстановления

Сверять агрегаты и ограничения, а также работоспособность auth, test purchase, renewal и освобождения места в тестовом окружении. Бот production к тестовой базе не подключается; настоящие сообщения не рассылаются из restore-дрилла. Для реального восстановления вне короткого окна потребуется заранее согласованное независимое приватное резервирование или иной тариф. Публичные dumps, GitHub artifacts с production-данными и credentials запрещены.

Во время разработки Stage 1.3 production restore/rollback/reset не выполнялись. Изолированная миграционная проверка не является подтверждением полного PITR-drill или гарантией RPO/RTO.
