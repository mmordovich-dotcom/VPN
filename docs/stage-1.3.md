# Stage 1.3 — надёжность демонстрационной платформы

Развитие выпущенного Stage 1.2.5 (`ed0b033`). Сохраняются Fastify/Prisma/Vite, один `vpnaxon_bot`, пользователи, серверные сессии, три способа входа, SubscriptionEngine, MockPaymentProvider/виртуальный provider, история заказов, подписок и мест. Настоящие платежи, VPN, Aeza и платные ресурсы не добавлены.

## Очереди и атомарность

`telegram_updates` остаётся единственным durable inbox/reply outbox бота. Добавлены `next_attempt_at`, lease token/deadline, отметка начала отправки, безопасная ошибка и конечный DEAD. Ответы с кодами/ссылками входа по-прежнему не сохраняются в durable response. Отражённые Telegram сообщения очищаются до сохранения.

`background_jobs` обслуживает FULFILL_ORDER, LIFECYCLE, RECOVER, CLEANUP, NOTIFY. Это развитие PAID-recovery: подтверждение платежа и постановка задания активации фиксируются одной транзакцией; уведомления создаются в транзакциях изменения заказа/подписки. PAID остаётся источником истины для восстановления пропущенного outbox. `engine.tick()` — совместимый вход в ту же очередь, не второй планировщик.

Блокировки захватываются только внутри транзакции: `FOR UPDATE SKIP LOCKED` выбирает доступную запись, lease UUID ограничивает обновления конкретным владельцем. Активация и распределение мест сохраняют прежний transaction advisory lock и ограничения SQL. Два процесса могут принять разные задания; повтор активации уже завершённого заказа не создаёт новую подписку/VPS. Подтверждение выполнения отдельно от бизнес-транзакции допускает повтор после сбоя, поэтому бизнес-операции идемпотентны.

Lease — 60 секунд; перед сетевой отправкой фиксируется send_started_at и 30-секундное окно. Bot API ограничен 8 секундами. Старая lease не может подтвердить/перезаписать результат нового владельца. Восстановление просроченной lease выполняется следующим потребителем.

Backoff: 1, 2, 4… секунд, максимум час; учитывается ограниченный retry_after. Задания допускают до 8 попыток, inbox — до 5. Неисправимые ошибки завершаются DEAD. Отложенная отправка из-за ограничения частоты не расходует попытки ошибки. Бизнес-задачи имеют приоритет над необязательными уведомлениями.

## Доставка Telegram и неопределённые результаты

Нельзя обеспечить exactly-once внешнего sendMessage. Явный отказ Telegram 429/5xx позволяет повтор после backoff; 403 отмечает блокировку бота, другие постоянные ошибки останавливают попытки. Если запрос мог быть принят, но ответ потерян, результат считается неопределённым. При перезапуске отправка с send_started_at переводится в DEAD/DELIVERY_UNKNOWN, автоматически повторно не рассылается. Сбой записи подтверждения в PostgreSQL после успешной отправки также оставляет задачу в этом карантинном пути, не превращает её в свежую попытку. Это сознательный выбор против дубликатов: отдельное сообщение может потребовать проверки администратором.

Админка показывает такие случаи. Кнопка обычного retry для DELIVERY_UNKNOWN отключена; исправление требует сверки доставки, а не массового повторения. Повтор бизнес-операции при этом остаётся идемпотентным. Необязательные уведомления отправляются не чаще одного глобально примерно в 1,1 секунды и одного пользователю в 30 секунд; Telegram inbox дополнительно обрабатывает flood-control ответы провайдера.

## Два режима одного обработчика

- `BACKGROUND_MODE=inline` — значение по умолчанию, существующий Render Free. API запускает общий dispatcher при старте и каждые 15 секунд; webhook также инициирует цикл. Пока API спит, работа не выполняется. При пробуждении обрабатываются due-задачи и актуальное серверное состояние. 24/7 не гарантируется.
- Будущий standalone: `pnpm build:cloud:worker`, затем `pnpm start:worker`. Используется тот же BackgroundRuntime и та же база; Bot API polling не запускается. Цикл — 2 секунды. Для переноса обработки API получает `BACKGROUND_MODE=external`; standalone использует ту же проверенную конфигурацию. Даже при одновременном запуске режимов защищают lease, уникальные event keys и идемпотентный engine.

Новый worker-сервис не создан. Команды подготовлены для будущего явно согласованного хостинга. При SIGTERM/SIGINT новые claims прекращаются, текущая операция дожидается завершения в пределах shutdown deadline 25 секунд. При принудительной остановке оставшаяся работа сохраняется и восстанавливается по lease.

## Плановые операции

Минутные уникальные задания проверяют сроки и PAID-заказы; hourly cleanup очищает технические записи. Просроченные интервалы не воспроизводятся миллионами отдельных ticks: после простоя выполняется актуальная сверка состояния. Списки подписок/заказов обходятся по 100 записей с продолжением по UUID; expiry обрабатывается ограниченными пакетами. Heartbeat хранится в базе и показывает последний успешный цикл/безопасный маркер ошибки.

## Уведомления

За 3 дня, за сутки, после окончания, после успешного демо-продления и важных изменений заказа. Ключ включает событие и срок/заказ, поэтому повтор планирования не создаёт новое сообщение. Перед отправкой заново читаются данные PostgreSQL: пользователь ACTIVE, настройки, блокировка бота, текущие срок и статус. Продление делает прежние reminders неактуальными. После простоя трёхдневное напоминание не догоняется в однодневном окне; отправляется актуальное однодневное. Сообщение об окончании актуально до 7 дней, о продлении/заказе — до суток. Проверка актуальности производится непосредственно перед подготовкой сетевой доставки; транзакция PostgreSQL не может атомарно охватить внешний Telegram.

Оба необязательных вида по умолчанию выключены. В боте: «Моя подписка» → «Уведомления» или `/notifications`. Сохраняются шесть основных кнопок и две кнопки входа. Кнопки устанавливают явное on/off, повтор одного update не инвертирует выбор. На сайте настройки доступны из подписок. Включение влияет на будущие ещё не обработанные события, а не повторяет ранее пропущенные.

## API, админка, безопасность

См. [пагинацию](pagination-stage1.3.md). `/admin` возвращает агрегаты и ограниченные настройки, а не семь полных списков. Админка загружает только выбранную страницу, поддерживает поиск, статус, порядок и пустые/ошибочные состояния. `/admin/diagnostics` защищён ADMIN: очередь/inbox, задержка due-задач, heartbeat, ошибки восстановления, активные пользователи/VPS/места, состояние webhook. Публичные `/health` и `/ready` остаются минимальными. Исторический health stage 1.1 сохранён для совместимости; версия приложения находится в auth/config.

Серверные мутации ограничиваются по проверенному user ID; auth-лимиты Stage 1.2.5 сохранены. Корреляция запросов — серверный UUID и X-Request-Id. 4xx классифицируются как пользовательские отказы; 5xx — системные ошибки. В логи не передаются исключения провайдера, тела запросов, URL query, job payload, токены, cookies или leaseToken. Роль ADMIN и собственность данных проверяются сервером. Для нового ADMIN используются прежние защищённые ADMIN_TELEGRAM_IDS; публичного повышения роли нет.

## Хранение и выпуск

Истёкшие auth-технические записи удаляются спустя сутки после expiry, inbox terminal — спустя 30 дней, terminal jobs — спустя 90 дней, старые heartbeat — спустя 7 дней. Пакеты ограничены; пользователи, бизнес-история и AuditLog не очищаются. Неподтверждённые рабочие задания сохраняются.

Миграция `20261026000000_reliability` добавляет четыре таблицы, поля существующего inbox и индексы пагинации. Старые in-flight sends карантинируются для безопасного перехода; прежние DONE получают finished_at. Бизнес-данные не удаляются. До production нужны зелёный итоговый CI и согласованный выпуск по [плану развёртывания](cloud-deployment.md). Ветка GitHub и изолированная Neon-проверка не означают публикацию Stage 1.3 в Render.
