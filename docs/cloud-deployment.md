# Как запустить сайт и Telegram-бота через GitHub и Render без терминала

Все действия ниже выполняются в браузере. Понадобятся ваши существующие GitHub,
Render, Neon и один бот BotFather. Настоящие токены/пароли в переписку не отправляйте.
Архив содержит исходники, а не опубликованный сайт. Удалённый запуск здесь не выполнялся.

## 1. Обновите существующий репозиторий

Скачайте SharedVPS-Stage1.2-Unified.zip и распакуйте. Внутри папка shared-vps-platform.
Перед обновлением скачайте резервный ZIP текущего репозитория через Code → Download ZIP.
В Render временно отключите Auto Deploy и Blueprint Auto Sync: загрузка нескольких
папок через GitHub может создавать промежуточные неполные коммиты.

В существующем репозитории используйте Add file → Upload files. Загружайте **содержимое**
папки shared-vps-platform в корень репозитория; не создавайте второй вложенный проект.
Замените совпадающие файлы. Если GitHub ограничивает число файлов, загрузите apps,
затем packages, затем docs/scripts и корневые файлы отдельными порциями. `.github`
должна остаться в корне. Существующие migrations и pnpm-lock.yaml не удаляйте.
Не загружайте исходные ZIP, node_modules, dist, .env и work.

После полной загрузки откройте Actions → Verify foundation. Дождитесь зелёного
результата для последнего коммита. Все прежние проверки сохранены; интеграционные
тесты теперь включают Stage 1.2. Пока CI не завершён, Render не обновляйте.

## 2. Примените миграции в Neon

Используйте существующую Neon-базу. Перед изменениями создайте резервную ветку/копию
в интерфейсе Neon, если это доступно на вашем плане, или сохраните резервную копию
своим обычным способом. База и старая история не сбрасываются.

В Neon Connect выберите прямое соединение (без pooling), SSL `sslmode=require`.
В GitHub Settings → Secrets and variables → Actions сохраните эту строку как
Repository secret `NEON_MIGRATION_DATABASE_URL`. Не вставляйте её в исходники.
Если secret уже есть и актуален — менять его не нужно.

Actions → Cloud database migrations → Run workflow → ветка main.
Workflow сначала запускает Verify, затем `migrate deploy` и повторяемый seed.
Дождитесь зелёного migrate. В базе должны быть обе записи _prisma_migrations,
включая `20261016000000_unified`. При ошибке не используйте reset/db push:
проверьте прямой URL, SSL, выбранную базу и результат шага миграции.

## 3. Обновите тот же Render Web Service

Откройте существующий shared-vps-api. План **Free**. Root Directory оставьте пустым.
В Settings поставьте:

- Build Command: `corepack enable && pnpm install --frozen-lockfile --prod=false && pnpm build:cloud:unified`
- Start Command: `node apps/api/dist/main.js`
- Health Check Path: `/health`
- Node: 22.22.2.

Это значения полей Render, запускать команды у себя не нужно. Сайт теперь отдаёт
тот же сервис по `/`, API — по `/api/v1`, бот — через webhook. Отдельный платный
worker не создаётся. render.yaml сохраняет прежние сервисы; API build обновлён,
старый Static Site остаётся необязательной точкой перенаправления.

Скопируйте публичный HTTPS-адрес этого Web Service. Ниже обозначим его как адрес
платформы. В Environment задайте (без угловых скобок):

| Переменная | Значение |
|---|---|
| NODE_ENV | production |
| APP_MODE | demo |
| NODE_VERSION | 22.22.2 |
| API_HOST | 0.0.0.0 |
| LOG_LEVEL | info |
| PUBLIC_ORIGIN | HTTPS-адрес платформы без завершающего / |
| CORS_ORIGINS | тот же адрес без /; для нескольких — через запятую |
| DATABASE_URL | Neon pooled URL, sslmode=require, connect_timeout=15, connection_limit=3 |
| TELEGRAM_BOT_TOKEN | токен **существующего** бота из BotFather |
| TELEGRAM_WEBHOOK_SECRET | уникальная случайная строка 32–256 символов A–Z/a–z/0–9/_/- |
| TELEGRAM_BOT_USERNAME | username того же бота без @ |
| TELEGRAM_LOGIN_CLIENT_ID | Client ID из Login Widget в BotFather |
| ADMIN_TELEGRAM_IDS | ваши подтверждённые числовые Telegram ID через запятую, либо пусто |

Webhook secret можно сгенерировать менеджером паролей в браузере, выбрав минимум
32 случайных буквы/цифры. Это новый отдельный секрет, не токен бота. Не вводите
секреты в VITE_* и не делайте скриншоты Environment для публичных обращений.
Render PORT задаёт сам. Пустые необязательные TELEGRAM_* поля не добавляйте:
когда бот не настроен, уберите эти поля полностью, оставив публичный каталог.

Сохраните Environment и выполните Manual Deploy последнего прошедшего CI коммита.
Откройте адрес платформы, `/health` и `/ready`. `/ready` проверяет базу; `/health`
сохраняет прежний контракт stage 1.1 для совместимости мониторинга. Фактическая
версия платформы указана в интерфейсе и `/api/v1/auth/config` (stage 1.2).

## 4. Настройте тот же бот и вход

В BotFather откройте `/mybots` → своего бота. **Не создавайте нового.**
В разделе Login Widget добавьте Allowed URL: адрес платформы и URL её корня с `/`,
поскольку popup SDK использует origin + pathname как redirect URI. Полученный
Client ID внесите в Render. Для подписи выберите RS256 (значение по умолчанию).
В этой реализации применяется официальный popup Login SDK; Client Secret для
server-side code exchange не используется. Не передавайте его в браузер.

Откройте сайт → «Войти через Telegram». Подтвердите вход в официальном окне.
Если сайт пишет «Вход подготовлен», нажмите кнопку ещё раз: это сохраняет
пользовательское действие для открытия popup. Разрешите popup именно для платформы.

## 5. Дайте себе ADMIN и зарегистрируйте webhook

Если вы указали свой числовой ID в ADMIN_TELEGRAM_IDS, подтверждённый вход создаст
ADMIN автоматически. Если ID неизвестен, оставьте список пустым: сначала войдите
на сайт, скопируйте **свой UUID аккаунта**, показанный рядом с «Личный кабинет».
В собственном Neon SQL Editor выполните запрос, заменив UUID своим значением:

```sql
UPDATE users SET role = 'ADMIN'
WHERE id = 'ВАШ-UUID-ИЗ-ЛИЧНОГО-КАБИНЕТА'::uuid
  AND status = 'ACTIVE';
```

Это первоначальное назначение администратора владельцем базы, не публичная API-функция.
Не повышайте неизвестных пользователей. Обновите страницу: роль прочитается из БД.

Админ-панель → Telegram Webhook → «Зарегистрировать webhook» → «Проверить webhook».
Регистрация выполняется сервером и не раскрывает токен браузеру. Повторная регистрация
использует того же бота, накопленные updates не удаляет. Остановите старый polling,
если вы запускали его где-либо раньше: Bot API не разрешает polling вместе с webhook.
Откройте своего бота, нажмите Start. Должны появиться шесть кнопок основного меню.

## 6. Подключите Mini App и прежний Static Site

В BotFather для того же бота настройте Menu Button / Main Mini App URL:
`адрес-платформы/#/connect`. В самом боте кнопка «Подключиться» также предлагает
открыть Mini App через inline web_app. Персональные данные требуют подписанного
initData; простое открытие ссылки с чужим Telegram ID ничего не авторизует.
Покупки, подписки, инструкции и поддержка работают в чате без обязательного Mini App.

Если оставляете прежний shared-vps-web Static Site, сохраните его прежнюю build
команду и поставьте VITE_API_BASE_URL равным адресу платформы. После production
сборки этот адрес служит только входом с перенаправлением на Web Service. Сам
защищённый кабинет работает на одном origin с API. Не создавайте дополнительный
Static Site, если достаточно канонического адреса Web Service.

## 7. Проверьте тестовую покупку

На сайте: Каталог → оформить → подтвердить. В «Мои подписки» должны появиться срок,
виртуальный VPS и demo:access. После обновления страницы запись остаётся.
В Telegram «Моя подписка» должна показывать ту же запись для того же аккаунта.
Либо выполните первую покупку в боте — сайт покажет тот же результат.

В админке виден заказ COMPLETED, TEST/SUCCEEDED платёж, подписка и занятое место.
Для модели 3 + 1 нужны четыре **разных Telegram-аккаунта**, а не четыре нажатия
одного пользователя: повторная покупка активного аккаунта предлагает продление.
Отмена освобождает место, история остаётся. Продление увеличивает собственный срок.

## 8. Диагностика и бесплатные ограничения

- Каталог не загрузился: откройте `/ready`, проверьте pooled URL/SSL и миграции.
- LOGIN_NOT_CONFIGURED: проверьте Client ID. INVALID_LOGIN: Allowed URLs, RS256,
  правильный бот и часы сервера. INVALID_INIT_DATA: заново откройте Mini App.
- ORIGIN_REQUIRED: PUBLIC_ORIGIN/CORS_ORIGINS должны совпадать с адресом открытого сайта.
- Бот молчит: проверьте webhook в админке, токен/секрет, отсутствие старого polling,
  наличие ожидающих updates, Render Logs. Не вставляйте Bot API token в URL браузера.
- PAID с ошибкой: админка покажет безопасный lastError; после исправления повторите
  активацию. После пяти неудачных Telegram-доставок проверьте telegram_updates в Neon
  и причину ошибки; затем владелец базы может сбросить attempts=0,status='PENDING'
  **для конкретного update_id**, не удаляя остальные записи.
- Render Logs и GitHub Actions содержат статусы, без токенов и строк подключения.
  Тексты обращений и подписанные входы в логи запросов не выводятся.

Render Free засыпает после 15 минут без входящего трафика; запуск занимает около
минуты. Во сне не выполняются интервалы/доставка бота. После пробуждения очередь
и сроки восстанавливаются из PostgreSQL, но гарантии 24/7 нет. Neon тоже может
приостанавливать idle compute. Постоянные фоновые проверки раз в 15 секунд,
пока API активен, расходуют лимиты Neon и мешают его idle-паузе до сна Render.
Keep-alive обходов нет. Не выбирайте платный план и не добавляйте платный worker
ради этой демонстрации; контролируйте квоты в Billing обоих сервисов.

После успешного ручного запуска можно вернуть Render Auto Deploy=After CI checks
pass. Blueprint Auto Sync оставьте выключенным. При последующих изменениях схемы:
сначала проверка/ручные миграции, потом deployment совместимого приложения.
