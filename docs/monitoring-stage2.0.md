# Мониторинг AXON · Stage 2.0

Выбран UptimeRobot. Подготовлен monitoring-uptimerobot-stage2.0.json — декларативный план, НЕ файл автоматического импорта API. Все мониторы PAUSED, контакт null, страница AXON Status не опубликована. Аккаунт/уведомления/измерения этим PR не создаются. Нельзя утверждать, что мониторинг уже работает.

## Адреса и назначение
| Публичный адрес | Условие успеха | Что доказывает |
| --- | --- | --- |
| / | 200 и AXON | Витрина доступна, но не авторизация или оплата |
| /health | 200 и status ok | Процесс API отвечает, без доказательства БД/очереди |
| /api/v1/auth/config | 200, ожидаемый публичный режим | Публичный API доступен; нет персональных данных |
| /ready | 200 при доступной БД, 503 иначе | Только технический readiness; не публиковать детали БД |

В публичную AXON Status включать первые три компонента после начала реальных измерений. Историческое uptime не придумывать. /ready использовать как health-check хостинга или внутреннего сбора, не публиковать сведения о Neon. Никакие admin URL, query-токены, user IDs и строки подключения не передаются в status page.

## Render Free
Официальный Render Free засыпает после 15 минут без входящих запросов; запуск занимает около минуты. Пятиминутный монитор не даст уснуть и расходует общие часы. Поэтому текущий безопасный режим — мониторы выключены, разовые проверки по необходимости. Увеличение таймаута снижает ложные тревоги, но не решает keep-alive; не активировать монитор против Free как обход сна. UptimeRobot не заменяет always-on backend/worker.

После отдельного одобрения оплаченного always-on ресурса НА СУЩЕСТВУЮЩЕМ shared-vps-api и бюджета: HTTP(S), Free интервал 5 минут, доступный на плане timeout, оповещения только после подтверждения сбоя, уведомление о восстановлении. Конкретные задержки/повторные проверки выбрать по доступным настройкам аккаунта; не приобретать Pro ради них. Бесплатный план на дату проверки предоставляет 50 мониторов и 5-минутные проверки; публичную status page на домене сервиса подготовить в пределах Free. Кастомный домен/платные функции не включать.

## Закрытая диагностика
Новый /internal/monitor требует Authorization: Bearer INTERNAL_MONITOR_TOKEN, минимум 32 случайных base64url-символа. При отсутствии секрета всегда 401. Не использовать query string, браузерный JS или Git для токена. В production env токен НЕ установлен этим PR. Только обобщённые категории database/queue/worker; нет адресов, имён пользователей/платежей, количества клиентов, payload и исключений БД.
Код 200: БД доступна, нет DEAD/просроченных >5 минут задач, RUNNING heartbeat свежее 90 секунд. 503: degraded/unavailable. Неподтверждённые provider attempts UNKNOWN смотреть в защищённой /api/v1/admin/integrations; полная существующая диагностика остаётся за admin auth.
Перед передачей отдельного bearer-секрета UptimeRobot нужно отдельное разрешение владельца, проверка поддержки custom headers текущим Free-планом и безопасная форма. Если заголовки недоступны — монитор остаётся внутренним, без платного upgrade и URL с секретом. Для публичной status page закрытый компонент не выбирать.

## Проверка обнаружения и восстановления
CI проверяет 401, 503 при ошибке БД/очереди/heartbeat и возвращение 200 после устранения инъекции, без раскрытия ошибок. Это тест кода, НЕ доказательство доставки уведомления UptimeRobot.
После авторизации: подтвердить выбранный email/канал, создать PAUSED мониторы по плану, согласовать активацию после always-on. Отдельный безопасный тестовый компонент/эфемерный CI endpoint с контролируемым 503 → 200 позволяет проверить down/up и доставку; production для этого не останавливать. Зафиксировать время, фактическое получение обоих уведомлений и задержку. Пока аккаунт/контакт/always-on отсутствуют, внешний alarm/recovery не проверен.
