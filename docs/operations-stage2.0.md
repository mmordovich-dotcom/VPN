# AXON · обязательные условия непрерывной эксплуатации

Stage 2.0 не покупает ресурсы и не выдаёт технический PR за коммерческий запуск.

## Хостинг и обработчики
Существующий Render shared-vps-api остаётся Free. Для надёжного Telegram precheckout (ответ до 10 секунд), webhook/очереди и lifecycle необходим согласованный always-on backend и непрерывно работающий worker. В текущей однопроцессной модели inline допустим только при гарантированно работающем процессе; внешний worker уже предусмотрен Stage 1.3. До оплаты выбрать размещение/юрисдикцию, цену, RAM, egress, PostgreSQL pooling и предел расходов. Не включать искусственный keep-alive. UptimeRobot не исправляет сон Free. Render/Neon проекты и существующий бот этим PR не меняются.

## Данные и восстановление
Текущая Neon production и её настройки не затронуты; snapshot/restore не выполняются этим PR. Перед будущей добавочной миграцией: отдельное разрешение, бесплатная точка восстановления при доступной квоте, сверка fingerprints пользователей/подписок/обращений/цен/вместимости/журнала, затем точный migrate deploy. Не удалять snapshot для освобождения квоты без согласования и не покупать квоту автоматически.
Необходим независимый от Neon зашифрованный backup в согласованном хранилище с ограниченными правами, отдельным ключом, периодом хранения и проверенным восстановлением. Аккаунт/хранилище/бюджет пока не выбраны; production backup/export НЕ создан. Нельзя помещать сырые production dumps или ключи в GitHub artifacts/Git. RPO/RTO, расписание, ответственный и процедура удаления по сроку ещё не утверждены; нет ложных гарантий.
Новый CI restore drill выполняет pg_dump/pg_restore только в эфемерном PostgreSQL service (16/18), два отдельных случайных DB, синтетические fixtures. Сравниваются 14 таблиц и восстановление PaymentFoundation без повторной выдачи. Dump остаётся внутри контейнера, удаляется; выводятся только безопасные итоги. Это техническое доказательство процедуры, НЕ независимая резервная копия production и не измеренный RPO/RTO.
После разрешения внешнего backup: выполнить защищённую выгрузку, проверить контрольную сумму и расшифровку, восстановить в изолированную БД той же версии, сверить immutable ledger и бизнес-данные, запустить recovery в режиме без внешних доставок, измерить время; только затем считать restore проверенным.

## Наблюдаемость
Публичные /health и /ready не содержат строк подключения/пользователей/стектрейсов. /internal/monitor после отдельной настройки bearer-секрета выдаёт только категории. DEAD/overdue queue и stale heartbeat дают 503; восстановление проверяется с инъекцией в CI. ProviderAttempt UNKNOWN не должен автоматически пересылаться: защищённая /api/v1/admin/integrations + ручная/периодическая read-only reconciliation в test harness. Production scheduler новых внешних запросов НЕ включён. Метрики/ошибки существующего admin diagnostics сохраняются. Отдельная документация: monitoring-stage2.0.md.

## Бюджет и экономика
Три клиента по 170 ₽ = 510 ₽ валового поступления за 30 дней при полной загрузке, до комиссии, налогов, возвратов, Stars-конверсии и инфраструктуры. Старое допущение аренды 200 ₽ не является подтверждённым тарифом Aeza и не меняется этим PR. Из расчёта нужно вычесть реальную отдельную аренду VPS, always-on API/worker, БД, резервные копии, мониторинг и юридические/платёжные расходы. При одном/двух клиентах доход 170/340 ₽; общие расходы не делятся на вымышленные тысячи пользователей. Цена Stars и выручка от её вывода отдельно согласуются, курс не придумывается.
Перед любым платным ресурсом утвердить RUB-лимит на месяц и максимальную единичную операцию, актуальную quote с коротким сроком, валюту/налоги, уже зарезервированные расходы и резерв на возвраты/продления. validateQuote не заменяет атомарную резервацию ResourceFoundation и не является разрешением совершать покупку. LIVE бюджетный контроль и реальный provider lifecycle не включать, пока контракт Aeza не подтверждён.

## Кратчайший безопасный путь
1. Выбрать законного продавца/представителя и территории; решить локализацию/трансграничную обработку и проверить тексты юристом. Одновременно получить условия аккаунтов Stars/RollyPay/CloudPayments и Aeza.
2. Подключить sandbox секреты через защищённую форму с отдельного разрешения, выполнить реальную тестовую оплату/дубликат/сверку/возврат и resource test в независимом scope. Никакого SWE-PROMO. Там, где sandbox отсутствует, зафиксировать блокер и безопасный план минимального отдельно одобренного испытания.
3. Утвердить always-on/backup бюджет, включить независимый backup+restore и согласованные оповещения. Затем отдельный выпуск DEMO Stage 2.0 по release-stage2.0.md; LIVE включается только после всех коммерческих gates и отдельного разрешения.
Это завершение существующей системы, а не начало новых визуальных этапов.
