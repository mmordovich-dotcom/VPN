## Как развивать существующий provider seam

В engine уже есть VirtualProvider.prepare(id), default — чистая demo-строка. В packages/providers есть ServerProvider create/get/terminate и process-local MockServerProvider; engine его не использует. Оба — DEMO, ни один не выдаёт реальные ключи. Mock Map не является durable orchestration. Нельзя просто вставить сетевой Aeza create в prepare: вызов находится под DB lock, случайный server UUID пересоздаётся после rollback; удалённая покупка могла пройти до timeout и продублироваться при повторе.

Следующий согласованный технический этап должен расширить существующий ServerProvider и связать его с engine, сохранив pure mock default:

1. В отдельной добавочной миграции: provider_operations с уникальным стабильным operation key от allocation/order, request fingerprint, состояниями pending/submitted/unknown/succeeded/failed, provider order/resource IDs, retryAfter/lease/error category и cost quote snapshot. Reservation с TTL и accounting capacity остаётся в Postgres. Сначала отдельная Neon validation branch, никакого изменения production сейчас.
2. Короткая транзакция фиксирует оплаченный заказ, reservation и outbox/job. Worker забирает операцию с lease, освобождает DB lock, вызывает adapter. prepare не держит сетевой запрос в global transaction. Перед повтором после timeout — reconcile по сохранённому provider ID/idempotency contract, иначе UNKNOWN и ручная сверка; никогда новый create вслепую.
3. Adapter проверяет доступность/тариф/локацию/ресурсы, quote expiry, spend cap и разрешение покупки. Цена или capacity не берутся из client payload. Конкретные Aeza methods/schema включаются только после подтверждения действующего контракта. Production keys — только защищённые серверные env, минимальные права, не клиент и не лог.
4. После подтверждения готовности VPS — отдельная credential operation на каждого клиента: индивидуальный идентификатор/секрет, зашифрованное хранение и rotation/revoke. Один общий ключ на троих запрещён. Slot ACTIVE только после подтверждённого provision. Доступ и provider root credentials никогда не включаются в публичные DTO/audit.
5. Expiry/cancel сначала revoke индивидуального доступа с проверкой результата. Общий VPS не выключается из-за одного клиента. Drain/terminate — только при отсутствии активных клиентов, pending operations/долгов и после review периода хранения. Автоматическое удаление оплаченного ресурса не включать как cleanup technical jobs.
6. Provider rent/auto-renew и user expiry независимы. В расходах фиксировать currency/minor units, invoice ID, оплаченный период, quote и фактическое списание; резерв на underfill/продление. Состояния invoice unknown и недостаток баланса требуют alert, а не придуманного success.

До подтверждения API можно подготовить только контракт и сценарии. Существующие mock tests уже проверяют отказ prepare, сохранение PAID и restart/recovery; они не моделируют оплаченный внешний side effect. Обязательные sandbox contract tests следующего этапа: timeout до/после create, lost ack, restart при submitted, duplicate delivery, stale lease, expired quote, resource unavailable, cost cap, reservation expiry, per-client revoke, retain shared VPS, manual termination review. Для реального Aeza sandbox сначала получить официальные правила, не заменять его настоящей дешёвой покупкой.

## Платежи: что есть и чего нет

Сейчас только TEST/PENDING→SUCCEEDED/FAILED/REFUNDED; кнопка confirm намеренно имитирует деньги в APP_MODE=demo. Audit records сохраняются, но не являются независимым неизменяемым финансовым журналом. Нет live webhook, reconciliation, disputes, charge IDs или денежных возвратов. Refund исправление этого PR касается только DEMO.

Для цифровых услуг внутри Telegram [обязательны Stars/XTR](https://core.telegram.org/bots/payments-stars), включая Mini App; внешняя платёжная интеграция сама по себе не разрешает оплату картой внутри Telegram. Нужны successful_payment, сохранённый telegram_payment_charge_id, refundStarPayment, /paysupport и обработка споров. Возврат клиента на экран и pre_checkout approval не подтверждают списание. Официальная документация описывает отдельное test environment; в этом этапе существующий production-бот туда не переключается. [Developer Terms](https://telegram.org/tos/bot-developers) требуют соблюдения правил платежей/данных; условия получения rewards, доступность payout/KYC и применимое право проверяются до выбора денежной модели. Цена 170 RUB не эквивалентна фиксированной net-выручке от XTR.

Для независимого web checkout после отдельного продуктового/договорного решения возможен кандидат YooKassa: [подключение и документы](https://yookassa.ru/docs/support/payments/onboarding/docs) предусматривают договор/идентификацию, нерезидентов ведёт менеджер; [регистрация](https://yookassa.ru/docs/support/merchant/payments/implement/start) различает юридические статусы. Допустимость конкретной деятельности, страны, возраста/дееспособности и варианта самозанятости нужно подтвердить индивидуально, универсальный возраст или разрешение не установлены. CloudPayments также имеет [заявку резидентов](https://cloudpayments.ru/form-residents) и отдельный путь зарубежного бизнеса; наличие формы не означает одобрения AXON. Не отправлялись заявки, реквизиты или документы.

Предлагаемое развитие существующих orders/payments/jobs без изменения текущих DEMO routes:

- Payment adapter выбирается на сервере по каналу/договору, client не выбирает test/live. Создание intent с сохранённым operation key и fingerprint суммы/валюты/order/user; стоимость только из order snapshot. Отдельные test keys и test account, в production DEMO не смешивать money и simulated events.
- Приём webhook: provider-specific authenticity. Для Stars — существующий secret-protected Telegram inbox + проверенный тип successful_payment; проверка invoice payload, payer/order, XTR amount, test/live окружения. Для YooKassa нельзя выдумывать HMAC: [официальные уведомления](https://yookassa.ru/developers/using-api/webhooks) предусматривают проверку текущего объекта через API и/или источника. За reverse proxy нельзя доверять произвольному X-Forwarded-For. Аутентифицированная API-сверка суммы, currency, merchant/test flag и идентификатора обязательна перед credit.
- Финансовый inbox с unique(provider,event/charge ID), append-only event journal и ledger effects с unique operation key. Сначала сохранить событие, затем ответить provider; trusted success + обновление payment/order + enqueue fulfillment в одной транзакции. Replay и out-of-order не должны повторять credit или понижать success до pending. Suspicious mismatch — quarantine, без выдачи доступа.
- Неизвестный результат create/capture/refund при timeout/500 — UNKNOWN + reconcile по сохранённому ID. [YooKassa interaction format](https://yookassa.ru/developers/using-api/interaction-format) описывает Idempotence-Key с окном 24h и неоднозначный HTTP500; локальная durable дедупликация обязана жить дольше. Нельзя после 24h слепо повторять financial POST новым ключом.
- Refund/dispute: отдельная подтверждённая операция, лимит возврата от captured amount, связь ledger→payment→order→entitlement, review доступа и исключение отката неприменённого продления. Запрос refund не равен завершённому возврату. Partial refunds, chargeback, tax receipt и policy должны быть определены до реализации.
- Reconciliation по расписанию: webhook lost, платёж есть без заказа, paid без fulfillment, refund unknown, расхождение settlement/комиссий. Денежный журнал сверять с provider settlement, не вычислять остаток из UI counters.

Эти таблицы/handlers не добавлены в production и не объявляются готовыми без выбора платёжного контракта. Независимая следующая реализация — isolated sandbox с реальной persistence и fault tests: forged/replayed webhook, wrong amount/currency/merchant/payer, pending→success, success→late fail, timeout/500, restart до/после financial commit, repeated refund, paid→provision failure→recovery, reconciliation. Ни одна кнопка/redirect не credit trigger.

## Инфраструктура и мониторинг

[Render Free](https://render.com/docs/free): общий лимит 750 instance-hours/workspace/month, idle sleep после 15 минут и около минуты на пробуждение; inline worker тоже спит. Нет бесплатного background worker. Не добавлять keep-alive обходы. Один always-on сервис в месяце 31 день использовал бы 744h, оставляя всего 6h другим сервисам. Фактический остаток смотреть Billing, а не оценивать по этой формуле. Paid workspace сам по себе не отменяет sleep Free compute.

До постоянных платных услуг согласовать always-on compute; начальный ориентир [Render pricing](https://render.com/pricing) $7/месяц за 512MB/0.5CPU (перепроверить в dashboard на момент покупки), а worker считается отдельно. Отдельный worker сначала не обязателен: inline сохраняет общую очередь; при росте вынести existing standalone mode, API BACKGROUND_MODE=external после проверки heartbeat. Pro workspace, Redis и новая БД сейчас не нужны и не куплены. Нужны замеры CPU/RAM/DB connections, queue lag и конкуренции lock; SLO не выдумывается из одного smoke.

[Neon pricing](https://neon.com/pricing): опубликованные Free 100 CUh/project/month, 1GB storage и ограниченное restore window до 6h/1GB changes. Фактический проект имеет 21600s retention; независимый backup/restore drill не подтверждён. Launch указан как usage-based $0.106/CUh и $0.35/GB-month плюс дополнительные услуги; typical spend не минимальный обязательный тариф. 0.25CU continuously×720h≈180CUh/месяц: frequent inline DB polling при постоянно работающем API может не давать базе засыпать, значит нельзя рассчитывать на 100CUh при 24/7. Это оценка, не текущий счёт. Пул Prisma runtime, direct только migration, bounded concurrency; connection limit и timeout не изменялись.

Наблюдать отдельно: uptime /health; DB readiness /ready; public metadata; privileged diagnostics (не публиковать cookie); webhook state/pending/error time; heartbeat >90s; oldestDueDelay; DEAD/DELIVERY_UNKNOWN; PAID lastError; provision unknown; capacity/cost/expiry; storage/CUh/egress/build limits. Для DEMO sleep — ожидаемая деградация; для commercial отсутствие heartbeat/очередь >5min — сигнал оператору. Внешний alert destination, расписание дежурств и конкретные RPO/RTO требуют владельца; фальшивый monitor без получателя не создаётся. Регулярный мониторинг не использовать для удержания Free активным.

Резервирование: перед schema release приватная pre-release branch; независимые encrypted backups с минимальным доступом/retention и согласованным бюджетом; ежемесячный restore drill в изоляции, замер RPO/RTO, reconciliation новых financial events перед переключением. Подробный существующий [runbook](backup-recovery.md). Production restore или массовый replay без review запрещены.

## Воспроизводимая экономическая модель

Все следующие числа — гипотезы, не тарифное решение. P=170 RUB/client/month, C=200 RUB/VPS/month, n=0..3. Голая серверная себестоимость C/n, выручка nP. До комиссий, инфраструктуры, налогов и работы: n=1:170−200=−30; n=2:340−200=140; n=3:510−200=310. Себестоимость при n=1/2/3:200/100/66.67 RUB. Пустой сервер = −200. 310 RUB — не чистая прибыль.

Расширенная формула: contribution(n)=n×P×(1−f−r−d)−n×k−C−H/S, где f=комиссия/конверсия, r=резерв возвратов/ошибок, d=резерв простоя, k=фиксированная комиссия за платёж, H=общие infra/support/backup costs, S=число арендуемых VPS. Налог/зарплата добавляются отдельно по выбранной юрисдикции. Effective paid months, advance subscriptions и currency FX учитываются отдельно; Stars rewards не считать рублёвым acquiring с гарантированной фиксированной комиссией.

Иллюстрация (не реальный fee offer): f=5%, r=10%, d=5%, k=0, H=1000 RUB, S=10 → H/S=100. Тогда contribution при n=0/1/2/3: −300/−164/−28/+108. Fully filled server приносит 510 gross, costs=200 rent+25.5 fees+51 reserve+25.5 downtime+100 infra=402, остаток108 до налогов/труда. Break-even ceil((200+100)/(170×0.8))=3 клиента, occupancy threshold 73.53%; дискретно требуется три, один недозаполненный сервер может быть убыточным.

При S=10 и 24 клиентах (80% заполнение), тот же пример: revenue4080−rent2000−variable816−H1000=264 RUB до налогов/работы. При21клиенте:3570−2000−714−1000=−144. Если реальная C=600, полностью занятый VPS с allocation H/S=100 даёт408−600−100=−292: цену/модель нужно пересматривать с владельцем, не наращивать закупки. Для observed €5.93 C=5.93×фактический RUB/EUR+fees/tax; текущий FX не выбран и конверсия не выдумана.

Рабочий капитал отдельно от прибыли: минимум следующий период аренды всех S VPS + infra + обязательства возвратов + запас на инцидент. Нельзя оплачивать обязательную аренду только ожидаемыми будущими продажами. Три клиента пока бизнес-лимит, не доказательство ресурсной достаточности: нужен согласованный нагрузочный тест настоящего сервера после разрешения провайдера.

## Договорные блокеры и помощь сторонних сервисов

До commercial определить страну/контрагент, законного дееспособного продавца, владельца банковского/Stars payout аккаунта и KYC, допустимость назначения/перепродажи у Aeza/платёжного провайдера, налоги/чеки, consumer refunds, privacy/retention/обработчиков данных, cross-border transfers и обязанности оператора сетевого сервиса. Если владелец не может заключать договор самостоятельно — подтверждённый законный представитель/разрешённая форма регистрации по применимому праву, а не чужие реквизиты. Документы и возраст в чат не запрашиваются.

Подрядчик может помогать интеграцией, бухгалтерией, merchant-of-record или хостингом только по проверенному договору: кто продавец/обработчик, кто принимает деньги/жалобы/chargebacks, кто хранит данные, как расторгается и экспортируется история. Нужны scope прав, минимальный доступ и ответственность. Его участие не обходит Telegram Stars/договорные запреты/проверку деятельности. Запросы компаниям не отправлялись и обязательства не создавались.
